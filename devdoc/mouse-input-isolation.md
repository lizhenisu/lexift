# 首次打开标注工具条时的 Windows 鼠标输入隔离

## 现象与原因（2026-09-29）

进程启动后第一次按 Alt+A，鼠标指针有时会停住几帧；工具条出现时，指针又突然跳到鼠标实际移动到的位置。工具条等待就绪的总时间尚可接受，系统鼠标输入被中断则不可接受。调整钩子线程后，用户实测确认首次打开时鼠标已经流畅。

根因是划词手势使用的全局 `WH_MOUSE_LL` 钩子。Lexift 原先在随后运行 Slint UI 事件循环的线程上安装它。Windows 会向**安装钩子的线程**发送消息来调用低级鼠标钩子回调。该线程同步创建或显示工具条、画布时，无法及时处理钩子消息，因而拖慢 Lexift 之外的系统鼠标输入。旧回调还同步分发划词事件，可能进一步增加延迟。翻译弹窗存在时，其外部点击钩子也曾由 UI 线程持有。Windows 的投递机制和专用线程建议见[微软 LowLevelMouseProc 文档](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelmouseproc)。

问题不是读取鼠标坐标太慢。仅比较渲染器耗时也无法解释系统输入停顿：从 FemtoVG 切换到 Skia OpenGL 虽缩短了部分 UI 回调，但低级钩子仍要等待 UI 线程处理消息。**工具条就绪时间与鼠标输入延迟是两项不同指标。**

## 线程边界与生命周期

```text
修改前：鼠标输入 -> 安装在 Slint UI 线程上的钩子 -> Core/UI 工作 -> 后续输入
                         ^ 创建工具条或窗口时，该线程无法及时处理钩子消息

修改后：鼠标输入 -> 专用钩子消息线程 -> 事件通道 -> 分发线程 -> Core/UI 路由
                         +-> 尽快调用 CallNextHookEx
```

Windows 平台的共用组件 [`hook_thread.rs`](../crates/lexift-platform/src/windows/hook_thread.rs) 启动独立消息循环，在线程内安装钩子，并在安装成功后才报告就绪。停止时发送 `WM_QUIT`，由同一线程卸载钩子后退出。[`selection_monitor.rs`](../crates/lexift-platform/src/windows/selection_monitor.rs) 的划词钩子将识别出的事件发给单独的分发线程。[`popup.rs`](../crates/lexift-platform/src/windows/popup.rs) 中弹窗外点击和前台窗口事件也采用这条边界；最后一个被监听的弹窗关闭时，停止相应的钩子和分发线程。应用退出时停止划词监听。窗口仍按需创建，没有增加常驻的隐藏工具条。

**后续 Windows 输入代码必须遵守的约束：**不要在 Slint 事件线程安装低级鼠标钩子；钩子回调内不要修改 Core 状态、执行 UI 工作、查询窗口、阻塞等待或逐事件写日志。回调只转发必要事件，尽快通过 `CallNextHookEx` 返回。手势处理和弹窗命中判断放在分发线程。即使 UI 正忙，钩子线程也必须持续处理消息。更快的渲染器不能代替这条线程边界。

## 验证结果与证据边界

首次按 Alt+A 时，外部进程每隔 5 ms 注入一次鼠标移动。每种渲染器在修改前后各以新进程运行十次。下表是**每次运行中单次注入调用最大耗时的范围**，不是工具条打开的总耗时：

| 渲染器 | 原先由 UI 线程持有钩子 | 钩子使用专用线程 |
|---|---:|---:|
| FemtoVG | 136–198 ms | 0.6–6.5 ms |
| Skia OpenGL | 10 次中有 9 次为 157–217 ms；另一次为 0.7 ms | 1.6–5.4 ms |

Skia 旧版那次较短的结果很可能没有在阻塞时段注入输入。应结合 `First annotation open timing` 日志分析，不能凭这一次认为旧钩子没有问题。原始本机记录位于 `target/annotation-gpu-cold-start/pointer-{baseline,new}-{femtovg,skia}.txt`；该目录是忽略的构建输出，上表已保留理解结果所需的数据。

还实测了划词拖动的开始和完成事件、Alt+X 打开翻译弹窗后在外部点击，以及两种钩子的两轮停止与重启。一次弹窗测试在停止时记录 `max_callback_us=12`、`max_dispatch_delay_us=20`。实现时平台与 UI 测试、workspace 构建、Clippy 和 Windows Release 构建均通过。请求以 120 fps 进行的 Desktop Duplication 录制，实际仅达到约 94 fps（CPU 编码）或 81 fps（NVENC），因此**不能**据此断言逐帧证明了 120 fps 下指针连续移动。受控的输入调用耗时与用户亲自确认的流畅度共同支持这次修复。

## 再次出现停顿时如何排查

1. 查清每个 `WH_MOUSE_LL` 钩子由哪个线程安装，该线程是否有独立消息循环。即使回调本身很快，安装线程收不到回调消息仍会阻塞输入。
2. 对照最长单次输入调用耗时与 `First annotation open timing`。若长 UI 阶段与长输入调用同时出现，先检查钩子线程是否被占用；工具条就绪时间不能代替输入延迟。
3. 查看停止时汇总的 `max_callback_us` 和 `max_dispatch_delay_us`。回调短但分发延迟增长，说明下游处理变慢，而钩子仍能及时返回。
4. 回归划词拖动、弹窗外点击、快速关闭重开和程序退出，确认事件仍能到达，钩子与分发线程也能释放。若要根据录屏判断视觉连续性，先确认捕获的**实际**帧率达到了目标。
