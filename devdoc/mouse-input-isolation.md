# 首次打开标注工具条时的 Windows 鼠标输入隔离

## 现象与原因（2026-09-29）

进程启动后第一次按 Alt+A，鼠标指针有时会停住几帧；工具条出现时，指针又突然跳到鼠标实际移动到的位置。工具条等待就绪的总时间尚可接受，系统鼠标输入被中断则不可接受。调整钩子线程后，用户实测确认首次打开时鼠标已经流畅。

根因是划词手势使用的全局 `WH_MOUSE_LL` 钩子。Lexift 原先在随后运行 Slint UI 事件循环的线程上安装它。Windows 会向**安装钩子的线程**发送消息来调用低级鼠标钩子回调。该线程同步创建或显示工具条、画布时，无法及时处理钩子消息，因而拖慢 Lexift 之外的系统鼠标输入。旧回调还同步分发划词事件，可能进一步增加延迟。翻译弹窗存在时，其外部点击钩子也曾由 UI 线程持有。Windows 的投递机制和专用线程建议见[微软 LowLevelMouseProc 文档](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelmouseproc)。

问题不是读取鼠标坐标太慢。仅比较渲染器耗时也无法解释系统输入停顿：从 FemtoVG 切换到 Skia OpenGL 虽缩短了部分 UI 回调，但低级钩子仍要等待 UI 线程处理消息。**工具条就绪时间与鼠标输入延迟是两项不同指标。**

## 线程边界与生命周期

```text
修改前：鼠标输入 -> 安装在 Slint UI 线程上的钩子 -> Core/UI 工作 -> 后续输入
                         ^ 创建工具条或窗口时，该线程无法及时处理钩子消息

修改后：鼠标输入 -> 专用钩子消息线程 -> 事件通道 -> 分发线程 -> Core/UI 路由
                         +-> 尽快调用 CallNextHookEx
```

Windows 平台的共用组件 [`hook_thread.rs`](../crates/lexift-platform/src/windows/hook_thread.rs) 启动独立消息循环，在线程内安装钩子，并在安装成功后才报告就绪。停止时发送 `WM_QUIT`，由同一线程卸载钩子后退出。[`selection_monitor.rs`](../crates/lexift-platform/src/windows/selection_monitor.rs) 的划词钩子只复制按下／松开的坐标和原始 Windows 时间戳，由单独的分发线程查询目标窗口、过滤本程序窗口并识别手势。[`popup.rs`](../crates/lexift-platform/src/windows/popup.rs) 中弹窗外点击和前台窗口事件也采用这条边界；最后一个被监听的弹窗关闭时，停止相应的钩子和分发线程。应用退出时停止划词监听。窗口仍按需创建，没有增加常驻的隐藏工具条。

**后续 Windows 输入代码必须遵守的约束：**不要在 Slint 事件线程安装低级鼠标钩子；钩子回调内不要修改 Core 状态、执行 UI 工作、查询窗口、阻塞等待或逐事件写日志。回调只转发必要事件，尽快通过 `CallNextHookEx` 返回。手势处理和弹窗命中判断放在分发线程。即使 UI 正忙，钩子线程也必须持续处理消息。更快的渲染器不能代替这条线程边界。

## 验证结果与证据边界

首次按 Alt+A 时，外部进程每隔 5 ms 注入一次鼠标移动。每种渲染器在修改前后各以新进程运行十次。下表是**每次运行中单次注入调用最大耗时的范围**，不是工具条打开的总耗时：

| 渲染器 | 原先由 UI 线程持有钩子 | 钩子使用专用线程 |
|---|---:|---:|
| FemtoVG | 136–198 ms | 0.6–6.5 ms |
| Skia OpenGL | 10 次中有 9 次为 157–217 ms；另一次为 0.7 ms | 1.6–5.4 ms |

Skia 旧版那次较短的结果很可能没有在阻塞时段注入输入。应结合 `First annotation open timing` 日志分析，不能凭这一次认为旧钩子没有问题。原始本机记录位于 `target/annotation-gpu-cold-start/pointer-{baseline,new}-{femtovg,skia}.txt`；该目录是忽略的构建输出，上表已保留理解结果所需的数据。

还实测了划词拖动的开始和完成事件、Alt+X 打开翻译弹窗后在外部点击，以及两种钩子的两轮停止与重启。一次弹窗测试在停止时记录 `max_callback_us=12`、`max_dispatch_delay_us=20`。实现时平台与 UI 测试、workspace 构建、Clippy 和 Windows Release 构建均通过。请求以 120 fps 进行的 Desktop Duplication 录制，实际仅达到约 94 fps（CPU 编码）或 81 fps（NVENC），因此**不能**据此断言逐帧证明了 120 fps 下指针连续移动。受控的输入调用耗时与用户亲自确认的流畅度共同支持这次修复。

## 再次出现停顿时如何排查

1. 查清每个 `WH_MOUSE_LL` 钩子由哪个线程安装，该线程是否有独立消息循环。即使回调本身很快，安装线程收不到回调消息仍会阻塞输入。
2. 对照最长单次输入调用耗时与 `First annotation open timing`。若长 UI 阶段与长输入调用同时出现，先检查钩子线程是否被占用；工具条就绪时间不能代替输入延迟。
3. 查看停止时汇总的 `max_callback_us` 和 `max_dispatch_delay_us`。回调短但分发延迟增长，说明下游处理变慢，而钩子仍能及时返回。
4. 回归划词拖动、弹窗外点击、快速关闭重开和程序退出，确认事件仍能到达，钩子与分发线程也能释放。若要根据录屏判断视觉连续性，先确认捕获的**实际**帧率达到了目标。

## 首次矩形拖动的短暂停顿（2026-10-06）

### 两条独立链路

此次复查发现：划词钩子虽已在专用线程上，按下回调仍同步执行 `WindowFromPoint`、进程查询、双击设置读取及手势判断；移动回调没有这段处理。现在把这些工作移到原有分发线程，保留 FIFO 顺序与原始事件时间。超过 500ms 的积压样本丢弃并重置手势，避免根据过期位置识别点击；停止时废弃未处理样本。受控测试让窗口解析停在门闩上，验证发送后续松开样本不必等待解析完成。**这证明线程边界，不证明本次拖动中途停顿由钩子造成。**

矩形预览则发现另一条可复现的冷路径：首次拖动才提交原生场景，后台创建 GPU 资源时，UI 使用全屏软件栅格与呈现回退；原生就绪后还需清除输入画布的软件像素。首次回调明显慢于后续同一会话的矩形。现在画布与工具条就绪后，异步提交空原生场景，把资源创建及软件／原生交接提前到首次绘制前。准备归当前会话持有，关闭时释放；不等待准备完成，不启动屏幕采集，不增加固定延时。若用户在准备完成前立即绘制或原生能力不可用，仍保留正常软件回退，不能保证所有时机都已预热。

### 有限诊断

使用 `RUST_LOG=warn,lexift_ui::annotation_drag_timing=debug,lexift_platform::annotation_drag_timing=debug` 开启诊断，默认不采样。每次按下后只采前 500ms，每项最多 128 个样本，松开／取消输出一条汇总，关闭清理状态；不逐事件写日志。

- UI 汇总记录输入处理、场景编译、软件栅格、提交与交接、原生完成轮询及整个渲染回调耗时，数组顺序为 `[median,p95,p99,max]`。
- `input_gap_ms` 是 UI 收到移动事件的间隔；`frame_gap_ms` 是渲染回调完成的间隔。Windows 移动消息会合并，二者不能充当硬件事件延迟或实际屏幕帧间隔。
- 原生汇总记录消息队列年龄与窗口输入回调耗时。队列年龄使用 `GetMessageTime`／`GetTickCount`，按毫秒量化，不是设备到光子的延迟。
- GPU 资源创建耗时在工作线程创建完成时记录一次。CPU 呈现确认不是显示器扫描完成；本轮未用高速录屏证明输入到实际显示的延迟。

工具切换、弹窗线程启停保留现有实现。本轮没有测量证据支持扩大这些路径的重构。

### 对照方法与复现范围

修改前后使用相同 Debug 构建配置、同一台机器和相同外部脚本，测量期间不运行编译。空文档分别测进程首次、连续、切换工具后首次、重开会话首次；普通标注及实时马赛克文档分别测填充后首次、连续、切换工具后首次和重开填充后首次。已有内容必须先绘制，因此这些组不能称为“进程首次”。每组 30 次，100%／125% 两块屏幕各 15 次，每个版本共 360 次矩形拖动。首次拖动在工具条就绪、定位和选择矩形后进行，不代表窗口刚显示瞬间即按下的极限时机。

外部脚本目标每 5ms 注入一次移动并调用 `GetCursorPos`，每次拖动 600ms。实际注入间隔也保存：系统休眠粒度会使部分移动成批到达，不能把目标 5ms 当作真实固定频率。输入调用耗时与坐标采样用于和无 App 的同机基线比较，不代替硬件指针或光子计时。

UI 只保存有限分位摘要。跨次比较使用**每次拖动最大值的中位数、P95／P99 与最大值**，不是把摘要再组合成逐事件 P95／P99。原始外部样本保存在 `target/drag-{baseline-clean,fixed-clean}-samples.json`，UI 日志为同名前缀的 `.out` 文件；构建目录不纳入提交。测试夹具位于正坐标屏幕，负坐标使用已有坐标回归，不宣称实机覆盖。

| 空文档／会话重开首次 | 41.348 | 4.054 | 58.096 | 5.967 | 65.734 | 6.251 |

空文档进程首次的移动到达间隔最大值中位数从 58.532 降到 18.276，P95 从 73.080 降到 19.865；渲染回调完成间隔最大值中位数从 64.605 降到 32.195，P95 从 79.505 降到 33.096。修正版全部 360 次采样均没有软件栅格回退；原版普通文档填充后的部分慢段仍来自原生交接。连续绘制和已有实时效果基本处于相同数量级，不能宣称所有工具按钮都出现过同一个根因或都得到明显加速。

外部逐事件输入调用（移动注入＋坐标读取）数据如下，无 App 组 30 次拖动／3,600 个样本，其余各 360 次／43,200 个样本：

| 状态 | 中位数 | P95 | P99 | 最大 |
|---|---:|---:|---:|---:|
| 无 App | 0.322 | 0.897 | 1.173 | 2.274 |
| 原版 App | 0.333 | 1.021 | 1.406 | 12.497 |
| 修正版 App | 0.339 | 1.006 | 1.289 | 12.339 |

原生消息年龄的每次最大值 P95／P99 为 16／16ms，最高 47ms；窗口输入回调的每次最大值 P95／P99 为 2.321／2.908ms，最高 16.180ms。存在离群值，不能说系统输入的全部偶发尖峰已经消除。一次独立退出审计记录修正版低级划词钩子回调最大值 23μs、分发等待最大值 36μs；这不是 360 次矩阵的配对数据，也不足以证明钩子是本次中途停顿根因。

Release 实机检查了两块屏幕的四向矩形、撤销、椭圆、荧光笔及实时／贴纸笔刷并保存截图。录屏目标 60fps，实际平均为 49.40／50.37fps（125%／100%，247／251 帧，5.00／4.98 秒，未补帧），只作为交互记录，不作为高刷新率逐帧连续或光子延迟证明。Platform／UI 测试与单独钩子停止重启、UI／Platform Clippy、格式检查及 Windows Release 编译通过。新增诊断还覆盖了 TLS 已销毁后的安全清理。

退出审计另发现既有问题：已使用 GPU 绘制后从托盘退出，`tray_menu::Registry` 的 TLS 仍持有 `WindowLifecycleCallbacks` 中的渲染 Port，过晚销毁时 `WindowsAnnotationRenderPort::drop` 的线程 `join()` 报 `threads should not terminate unexpectedly`；原版测量版本也出现退出异常。为取得原始调用栈曾临时替换 panic 输出，随后完整恢复，未改动观测模块。本轮不扩展 GPU／托盘退出重构，后续应在退出事件循环前显式释放托盘注册表持有的回调与 Port。
