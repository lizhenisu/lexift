# Windows 录屏画面裁剪验证

本轮从 `0ef0356` 开始。画面裁剪按原视频的偶数像素边界保存，与首尾裁剪组合。预览仍由原 Media Engine 和 D3D11 交换链呈现。MP4 的 NV12 裁切按两个平面分别取行，GIF 的两遍 RGB 解码都使用同一个画面范围。

Core、App、UI 和 Platform 的录屏回归共通过 96 项，32 项按原测试标记忽略。轮询检查、格式和全工作区严格 Clippy 通过。

Windows 原生夹具从 160 × 120 的有声 H.264 源裁下 80 × 64，独立解码得 MP4 36 帧、AAC 音轨和 GIF 18 帧。一帧区间也分别产出 80 × 64 的单帧 MP4 与 GIF。所有解码画面抽查了两侧色块和单调时间戳。原生预览读取交换链对应像素为 BGRA `[241, 0, 0, 255]`，符合保留区域内的蓝色标记。

最终 Release 的 100%／125% 原生流程均从真实录制预览进入裁剪。125% 场景先拖动后取消，再进入裁剪并恢复完整画面，最后重新拖出范围并应用，保存 MP4 为 1056 × 594、64 帧；100% 场景应用 1920 × 1080 输入的裁剪范围后保存 GIF 为 960 × 540、32 帧。裁剪后的视图按新比例继续停在当前时间位置，首尾范围和静音状态保持。

最终构建 SHA256 为 `68397A0EDC515219736AAADA04EE73725BE5C42C9B3C09D2B0052AB1C25CACE0`。首次最终 GIF 对话框脚本没有完成扩展名切换，保留在原始日志中；使用相同 Release 单独重试后，原生对话框正确输出 `.gif` 并完成独立解码。该次失败归因于测试对话框操作，产品压缩失败计数不包括它。
