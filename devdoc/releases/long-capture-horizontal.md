# Windows 横向长截图验证

基线为 `759f6b5`，实施分支为 `codex/long-capture-horizontal`。采集会话默认纵向，方向可在首帧呈现后、首次追加前切换。方向请求和采集帧在同一个 worker 结算。横向在后台转置单帧，用列条带复用配准、历史定位和裁剪，预览和输出使用正常行序。横向重叠必须逐像素一致，固定栏识别和自动滚动用于纵向。

## 自动化

Core 的非对称列夹具覆盖首帧直接完成、短步追加、方向锁定、滚回、左右裁剪和续接。预览和导出分别与参考区间逐像素对照。固定侧栏和丢失重叠保留已确认结果。工作流覆盖过期请求、首次追加胜出及配置期间阻止自动滚动。

Core 24 项、App 5 项和 UI 11 项通过。App 验证切换方向会重新处理同一采集序号的最新画面。UI 软件渲染覆盖十二语言、浅深主题、100%／125% 和两种方向的控制条。Platform 原生纵向回归验证了 15 个物理偏移下的连续采集和逐像素拼接。格式、Slint 编译、严格 Clippy 及 Windows Release 构建通过。

## Windows Release

构建 SHA256 为 `8939977f8e42e2d2e36e74a18feea5ebf2c4dce8ea34096cbedf0783e29329e5`。`final-native` 在 100%／125% 双屏实际切换方向、向右追加、滚回、使用 K 裁掉右侧及再次追加。两屏剪贴板均为 960×400，并逐像素匹配同一列号参考图。

`native-left` 在两屏通过 J 裁掉左侧，经过仍保留的列时仅更新位置，回到尾部再追加，最终剪贴板为 840×400，与参考图的列区间逐像素一致。`final-browser` 在两屏使用 Chrome 的本地列号图和内嵌横向滚动区，实际接收横向滚轮，分别验证复制和常规 PNG 保存。四份 960×400 成品与参考图逐像素一致，包含对采集边框、控制条和预览排除的验证。通过原生窗口样式和所有者检查保存对话框的辅助窗口身份。

`extras-output` 在双屏验证暂停期间画面保持、恢复后继续追加、取消后重开、贴图复制、进入编辑后复制和快速保存。六份 840×400 输出均与参考图逐像素一致。首次快速保存通过原生文件夹选择器，退出测试后恢复原配置。

双屏 `final-native` 每轮处理 7 帧，包含 1 次历史定位和 1 次裁剪。累计匹配耗时 11.46～12.90ms，历史定位帧 0.42～0.67ms，累计预览生成与调度 1.93～2.42ms，最终展平 0.47～0.48ms。拼接器保留像素峰值 3,456,000 字节，计入该 worker 的输入、转换和展平缓冲后估算峰值为 5,376,000 字节。原生采集器及进程工作集另有资源归属。

早期脚本曾在按键选择方向、填写保存文件名和点击编辑器工具条时超时，原始日志仍保留。最终脚本依据菜单实际边界和原生保存控件完成交互，编辑器工具条的复制位置也已修正。极窄工作区、接近资源上限的横向原生采集及第三方真实页面内容未纳入原生矩阵；有界预览、资源上限及不可靠匹配由自动化覆盖。

专项脚本、构建日志、合成列号图及原生记录保存在忽略的 `target/long-capture-horizontal/`。
