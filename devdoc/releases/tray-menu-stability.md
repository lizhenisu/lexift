# 托盘菜单连续打开验证

日期：2026-10-26。分支 `codex/tray-menu-stability`，起点 `main` 的 `171eb3c`。实施阶段未自动暂存、提交、合并或推送；验证完成后按用户明确授权提交并快进合入 `main`，不自动推送。证据位于忽略的 `target/tray-menu-stability/`。

## 结论与根因范围

此前“第二次打开托盘菜单超时”已证实包含自动化定位和就绪判定错误，不能据此认定是产品焦点故障：

- 原脚本依赖之前取得的 `Shell_NotifyIconGetRect` 坐标，且据此推断溢出区是否展开。实际 Shell 重排后，注册范围与先前可访问范围暂时不同；失败截图中点击打开了 Windows 安全中心菜单，另一次命中了其他应用。对应观察未出现新的 Lexift 菜单窗口或所属原生请求。
- `FindWindow` 测试桥接将 PowerShell 的 `$null` 作为托管空字符串传入，导致带标题的溢出窗口查找失败。脚本桥接现将空字符串转换为 Win32 的空指针语义。
- 原菜单查找要求固定标题及 240～500px 高度。125% 下实际菜单显示阶段曾为 503px，重新布局后为 456px；固定范围会漏识别已出现的菜单。
- 修正定位器后，未修改的当前 main Release 完成鼠标 5 轮、Shift＋F10 5 轮，包含 Escape 与外部点击关闭。证据：`baseline-registered-settled/`。基线 SHA256 为 `8FF4E291F05995C81CEA1200858589CA095C3423475BB0B5410BCF063EA14DC4`，对应 `171eb3c`；此前旧倍率产物仅保留为辅助证据。

正式结论是修正脚本并补强请求生命周期隔离，**不宣称修复了尚未证实的产品激活缺陷**。所有首次失败及定位过程保留，不将失败轮次重新标为通过。

## 源码修改

- 现有 `TrayMenuRequest` 增加进程内递增 `request_id`，Platform 分配，App 原样转发；UI 拒绝重复及已退役编号。
- 请求编号与菜单 generation 共同约束准备、延迟定位、原生输入、动作和关闭回调，防止旧实例操作新窗口；动作与关闭竞争时最多执行一次动作。
- `debug` 诊断覆盖原生请求、转发、排队耗时、准备、显示／激活、失焦、关闭原因、动作和销毁。保留原生 dismissal cause，区分各初始化失败阶段；无鼠标移动日志、正文或图片内容。
- 保持原有一次激活、显式取消且仍有焦点才归还通知区焦点、有界隐藏准备及窗口销毁策略。没有新增轮询、钩子、固定等待、隐藏窗口缓存、业务功能或可见文案。
