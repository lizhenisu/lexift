# Windows 长截图自动滚动验证

自动滚动复用单屏实时采集和纵向配准。控制条每次从手动模式打开。等待目标时检查指针、物理选区和前台窗口，运行时每次只注入一档向下滚轮。帧确认和稳定时间决定下一档，延迟、窗口变更或暂停使旧代次无法继续输入。使用方法见[纵向长截图](../features/screenshot-mode.md#纵向长截图)。

## 原生场景与证据

夹具与日志在忽略的 `target/long-auto-scroll/`。Windows 实机使用 125% 和 100% 两屏，使用真实热键、鼠标、滚轮和剪贴板。文档夹具以 Win32 桌面窗口显示带行号的确定性图案，浏览器使用独立 Chrome 测试进程和本机页面。

| 场景 | 核对项 |
| --- | --- |
| 本地文档滚到底 | 16 档有效滚轮，额外一档后判定画面未变化。复制 600×2000，逐像素等于参考图。 |
| 移出选区、手动续接 | 自动滚轮停止，手动滚轮追加，复制结果等于参考前缀。 |
| 等待超时 | 控制条保持准备状态直到超时，夹具没有收到滚轮。 |
| 暂停、继续、取消重开 | 暂停后继续保持手动。取消后确认范围、预览和控制窗口退役，连续用例使用新会话。 |
| 切换前台 | 另一个受控窗口取得前台并保持，原目标和新目标都没有收到后续自动滚轮。 |
| Chrome 正文与内嵌滚动区 | 滚轮只进入选中的正文或内嵌区域。两屏完整输出与 600×2000 参考图逐像素一致。 |

原始尝试保留了脚本按钮坐标过期、窗口重叠及准备后立即点击造成的前台交接超时。浏览器最早的 100% 测试还发现夹具侧栏覆盖了参考区，已移到参考区外。脚本以实际窗口归属、前台和首屏像素作为进入条件。

Core 和替身覆盖重复帧、稳定期、绝对步长截止时间、重叠不足、长度上限、旧代次及输入拒绝。普通权限进程对管理员窗口的输入拦截通过替身模拟。

## 最终构建

最终 Windows Release 的 SHA256 为 `60B22E74C47141DC908FDC45B8A9FD808E9FD41514F5A9214D254FFC2EC50742`。`final-local/`、`final-lifecycle/` 和 `final-chrome/` 共 16 个双屏场景通过。手动续接用例还在同一次采集中重新启动自动滚动，再次移出后确认没有多余输入，输出为逐像素一致的 600×900 参考前缀。三个测试进程均通过托盘退出。

`timings.json` 保存逐场景统计。工作线程观察到启动至首次确认新行约 609–642ms，包含夹具的焦点交接和指针等待。单档发送至确认的新行耗时最长约 95ms，稳定等待单独计入后续调度。

Core 长截图 14 项、App 采集 2 项及自动滚动输入 1 项、UI 长截图 11 项、Platform 235 项通过。Slint 编译、格式检查和 workspace 严格 Clippy 通过。
