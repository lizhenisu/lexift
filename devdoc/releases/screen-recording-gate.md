# 屏幕录制技术验证

本轮代码只编入 Platform 测试可执行文件，不提供正式录制入口。分支为 `codex/screen-recording-gate`，基线为 `b29d7b9`；既有 PixPin 研究文档保留。

**当前结论（2026-10-31）：软件 1080p30 必测门槛通过，可支持后续无声 MP4 正式首版接入。硬件没有合格候选：AMD 色彩检查失败，NVIDIA 资源退役检查失败；未修复、未准入，不将视频可解码等同于硬件验收。** 本轮仍不接正式入口。最终数据见文末；早期失败和进度记录保留。

## 实现边界

- Core 纯时间线按绝对帧号计算 100ns PTS，扣除暂停时间。
- 独占显示器 WGC、两帧池、区域 staging 读回；不经过效果采样合成器。偶数尺寸、单显示器、设备和布局校验。
- 独立 MTA 编码线程使用 Media Foundation Sink Writer，NV12／BT.709／H.264 High，1080p 30fps 12Mbps，低延迟请求；实际实现模块记入每轮 JSON。
- 三份 BGRA 源缓冲、NV12 转换及提交缓冲保守预算 31,104,000 字节；编码器、GPU、诊断 JSON 和系统内存另计。队列只保留最新源帧，超过一秒积压失败。
- 暂停不提交新帧；恢复校验新鲜采集时间和 epoch。停止封尾后重命名临时文件；取消清理所属临时文件，资源释放前拒绝重开。
- 原生合成夹具有持续范围框、排除控制块和提示块。它们是技术夹具，不代表正式控制条界面。

## 重复执行

先运行 `cargo test -p lexift-platform --release --lib recording_gate --no-run`，取得输出的测试 EXE。

```powershell
scripts/validate-screen-recording.ps1 -TestExe <测试EXE> -EvidenceDirectory target/screen-recording-gate/new-run -Region 320,200,2240,1280 -Rounds 20
python scripts/validate-screen-recording.py target/screen-recording-gate/new-run --ffmpeg <ffmpeg.exe> --ffprobe <ffprobe.exe>
```

证据目录必须不存在，驱动保留旧失败记录。FFmpeg 仅为独立测试解码器，不属于应用依赖。录制主体由自有合成源覆盖，全屏底边可能包含真实 Shell；不采集个人应用窗口正文，所有视频只存于忽略目录。

## 已发现并修正

- 125% 下线程 DPI 虚拟化导致物理采集范围被拒绝：采集所属线程显式使用 Per Monitor V2。
- WinRT 空帧在 windows-rs 投影为 HRESULT 0 错误：作为暂无帧处理。
- 原生 STATIC 默认重绘覆盖已知像素：改为没有背景刷的测试窗口类。
- 恢复夹具动态状态被静态阶段覆盖，导致等待新鲜帧超时：修正阶段边界。
- 合并帧通知未复位造成首帧后仅超时读回，实际约 25fps：读取前重新启用通知。保留修复前证据。

#### 硬件探测结论修订

原 `0x80070057` 定位于 `create_sink_writer`。原因是同时启用硬件 MFT 与禁用格式转换；[Microsoft 属性契约](https://learn.microsoft.com/en-us/windows/win32/medfound/mf-readwrite-enable-hardware-transforms) 禁止该组合。已改为仅软件路径禁止转换，保留原失败证据 `hardware-stage-probe/`。

修正后 `hardware-fixed/` 实际使用 AMD `amdh264enc64.dll`，硬件属性为真，完成 MP4 编码；但全程色块检查在首帧红色色块测得 `[205,31,69]`，期望 `[220,50,70]`，超过固定容差，**实际失败，未验收**。`hardware-negotiation/` 记录输入／输出均协商 BT.709、有限范围、1080p 30fps、High、12Mbps，不能因这些参数或文件可解码而忽略颜色错误。尚需继续定位实际像素链路，不放宽容差。

本轮尚未完成：明确绑定并遍历硬件候选、硬件色彩修复、真实写入中及封尾失败、控制窗口可操作性、完整取消竞争／资源计数、负坐标及设备失效原生补验、最终无干扰双屏复测与增量诊断十分钟长测。**专项仍未完成，不接正式入口。**

## 剩余矩阵收尾说明（2026-10-31）

本节取代上述历史进度；最终通过状态和统计须与所属证据目录一致。

### 已定位的问题与契约

- 显式绑定硬件编码器使用进程内 `MFTRegisterLocal` 工厂，并核对实际调用次数和实现模块；仅改变插件禁用列表并不能证明选中了指定编码器。
- 两个 AMD 枚举项均能编码 NV12，但当前驱动的 H.264 帧缺少所需 BT.709 色彩标记。容器标记、输入协商和编码成功均不等于解码颜色正确；保留固定色块检查失败，不修改容差、不修补码流、不将其列为合格硬件。输入类型枚举为空也不能推导为不支持 NV12。
- NVIDIA 显式绑定结果为 `nvEncMFTH264x.dll`，软件为 `mfh264enc.dll`；名称、CLSID 等可选接口缺失独立记录，不否决已经正确编码的文件。
- 硬件连续开关检查发现额外原生句柄随轮次增长。显式工厂持有的 `IMFActivate` 会缓存变换对象，不能只注销工厂并释放接口；选择守卫现随 Encoder 存活，在 writer 释放后调用 ShutdownObject。依据 [ActivateObject](https://learn.microsoft.com/en-us/windows/win32/api/mfobjects/nf-mfobjects-imfactivate-activateobject) 和 [ShutdownObject](https://learn.microsoft.com/en-us/windows/win32/api/mfobjects/nf-mfobjects-imfactivate-shutdownobject)，调用激活的一方负责关闭，不能依赖所属 Lease 计数归零推导驱动资源已释放。修复前完整矩阵保留在 `qualified/`，修复后另建证据目录。
- 采集主动关闭后再次析构造成原生快速失败，现将通知撤销和会话／帧池关闭改为幂等。原失败位于 `fault-final-capture_closed/`，修复复测位于 `capture-close-r2/`。
- 100% 全屏底边包含正常 Windows 任务栏。验证器按实际工作区区分合法 Shell 内容与本次青色范围框，不再要求任务栏像素等于合成背景；其余色块容差保持不变。原失败及修正后的报告均保留。
- ToolWindow 的 `Process.MainWindowHandle` 可能为零，外部焦点夹具改为按所属 PID 枚举真实可见窗口，通过实际点击切换焦点，未调用强制激活补救。
- 逐帧和进程采样均使用后台增量 JSONL；阶段诊断只保留有界的创建及封尾项目。CPU 像素预算不包括 GPU、编码器内部缓存、系统 DLL、测试夹具与进程分配器。
- 错误报告显式按 UTF-8 读取，避免中文系统错误在 GBK 环境导致检查器自身解码失败。`verifier-completion/` 的截断、错误帧数、缺失视频和注入错误像素四项均正确检出并生成结构化失败报告；可用 `scripts/validate-screen-recording-verifier.py` 重复执行。
- 最终夹具使用单份固定 MTA 编码服务串行执行请求，队列有界，不在阻塞时替换工作线程；每个录制的 writer、MFT、源帧、采集实例和窗口仍独立退役。`native-retired-*.json` 记录每轮销毁、join 完成后的实际进程句柄数，不能用运行峰值代替退役基线。

硬件资源对照保留 `hardware-retirement/`、`hardware-shutdown/` 和 `hardware-service/`：仅关闭激活对象、显式关闭异步 MFT（HRESULT 成功），以及固定 MTA 服务均未消除 NVIDIA 的逐轮原生句柄增长。固定线程五轮退役句柄为 508、523、542、557、574。当前无法将其归因于驱动或本地工厂接线中的具体一方，**不能标为已修复或合格硬件**。最终矩阵将颜色／解码通过和资源资格分别报告；首版正式接入只能采用通过全部必测条件的软件基线，硬件接入保留为独立阻断项。

句柄诊断保留完整逐轮序列和预热后的极差；资格检查比较预热五轮后首尾各五个退役采样的中位数，允许不超过 32 个句柄的变化。单次原生异步收尾的尖峰不等同于持续增长，也不能只看范围就认定泄漏。该诊断值不是业务资源预算，不替代窗口销毁、线程 join、自有资源归零和缓冲归还断言。所有逐帧视频、颜色及时间线检查保持原标准；资源汇总可用 `scripts/summarize-screen-recording.py` 对同一份完整证据重新执行。
