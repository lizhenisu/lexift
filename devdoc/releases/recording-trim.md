# 录屏首尾裁剪验证

基线 `main bad4ed4`，实施分支 `codex/recording-trim`。本轮实现精确帧范围、区间试听、后台重新编码与原子保存；完整范围继续复制原封尾文件。证据在忽略的 `target/recording-trim/`。

## 行为与所有权

范围使用原录像整数帧索引 `[start,end)`，最短一帧。把手拖动期间不提交，松手确认；左右键逐帧微调，取消拖动保留原范围。恢复完整范围不进入撤销历史。试听与定位限制在确认范围内，终点保持最后保留帧；静音仅影响试听。

Core 管理范围、版本、保存接纳、取消与关闭竞争；App 调度，Platform 持有原封尾文件、解码器、编码器和窗口资源，UI 只管理草稿和展示。打开及重建播放器时携带确认范围，第一张实际呈现画面属于该范围。播放停止由原生媒体时钟标记与帧路径边界检查控制，不由 UI 十次每秒的进度回调裁决。

先选择原生保存路径，再按需后台解码与重新编码。Source Reader 定位后读取关键帧前滚，依据实际 PTS 选择视频帧；按原尺寸、帧率、画质码率和 BT.709 输出 H.264，高质量声音沿用 AAC-LC／48kHz／双声道／192kbps。原始录像始终保留，取消或失败可重试，不在派生成品上累计压缩；裁剪保存会产生再次有损编码。

导出进度区分转码、封尾和发布。取消／关闭不在 UI 线程等待 COM；所属任务退役后才允许重开或执行丢弃确认。窗口、成品、请求及范围版本隔离旧回调。复制保存成品不进入图片历史，不修改 R。

## 原生门槛与发现的问题

- `native-matrix.json`：九个原生场景，包含关键帧之间开始、首帧、末帧、无声，以及十分钟真实录制的首／中／尾片段。独立完整解码的帧数与所选区间一致，逐帧条码等于原视频对应片段。
- `audio-independent.json`：对已有受控录制的完整解码 PCM 比较脉冲；选段内两声道的脉冲数量与毫秒位置一致，短至一帧仍保留音轨。AAC 解码尾部填充样本另外记录，不作为多出的源内容。
- `native-preview-r2.log`、`native-preview-audio-r3.log`：实际工作线程的选段停止及重播通过，诊断取实际交换链缓冲。持续音与独立短脉冲的回环时间差验证停止边界；不把物理扬声器或屏幕光子同步写成通过。
- `native-cancel.log`：同进程二十轮交替在准备后及转码中取消，原文件不变，编码器所属计数归零，临时文件可删除。
- `native-faults.json`：真实无效目标路径、明确标注的写入／封尾错误注入和后续成功编码；不把注入错误冒充真实磁盘故障。

已修复并保留首轮失败：1080 行画面使用 1088 行解码缓冲时按显示范围正确复制 NV12 平面；临近流末端改为显式交替读取音视频流；已有终点帧不再等待同帧定位产生新 tick；按下与提交同帧到达时不提前递增播放请求。重试直接携带范围，避免先呈现原片首帧。

初次持续音夹具使用硬切脉冲产生 AAC 边缘振铃，保留失败并改为已知 2ms 渐入渐出夹具，不修改产品音量或延迟。最初原生窗口测试未泵送父窗口消息导致子窗口创建等待，修正测试消息循环并保留超时。

补验发现恢复完整范围后，30fps 无声录像从结尾重播可能在首帧定位超时。保存首次失败及 `replay-before.log`：Media Engine 的异步定位有时落在第 1／2 帧，严格边界检查拒绝错误画面。修复等待原生定位完成，非零定位使用有界原生 FrameStep 修正邻近帧；回到第零帧则重新加载同一只读源，等待 LOADEDDATA 后才接纳目标画面。缓存画面不在加载完成前提前报告成功，定位期间不接纳旧的播放结束信号。仍以实际视频 PTS 和呈现内容确认。不放宽帧范围或将请求时间冒充实际画面。`replay-after-r10.log` 初次二十轮通过后，强化完成事件校验再次检出逐帧回退不稳定，保留 `replay-final.log`、`replay-final-trace.log`；未将初次通过作为最终结论。最终 `replay-r13.log` 在同一原生播放器连续二十轮完整播放、首帧定位及重播通过；`native-preview-audio-final.log` 同时复验非零区间音频停止。

`ui-pixels-r6.json` 独立完整解码此前十八段正式 UI 保存结果，逐帧条码与原录像所选区间一致；它们属于修复前构建，不替代修复后最终矩阵。麦克风准备中曾因真实设备启动时间戳不连续拒绝开始，保留首次失败，重新确认设备后可录制；没有静默改为无声。

### 性能与资源

`default-final-r10/` 每屏预热一次再测十次，对照同口径 `bad4ed4` 的 `recording-preview-validation/delivery-default/`；无并行编译或性能测试。原始数据和中位数／P95 见 `final-performance.json`。以下为 P95 毫秒：

| 阶段 | 125% 基线 → 最终 | 100% 基线 → 最终 |
| --- | --- | --- |
| 首个提交视频样本 | 162.70 → 163.63 | 162.39 → 157.96 |
| 停止至封尾 | 109.71 → 109.32 | 107.75 → 108.34 |
| 封尾至预览首帧交接 | 138.86 → 144.53 | 143.50 → 147.93 |

代表场景均未恶化超过 10%。正式矩阵记录的 106 次原生实际画面操作中位数 29.60ms、P95 136.26ms、最大 157.29ms；这组包含首次呈现、播放及定位，未将未产生新帧的缓存同帧交接伪装成新解码样本。最终原生二十轮取消的退役 P95 44.34ms，最大 47.55ms。短片和长片转码总耗时另见各门槛日志，未将任务入队当作完成。

1080p 所属受控转码视频缓冲记录为 9,354,240 字节，带声音场景 PCM 记录 16,128 字节；解码器、编码器、GPU 内部缓存和进程 PrivateBytes 另列，不宣称这些值等于进程峰值。预算仍为自有视频 64MiB、音频 8MiB。

二十轮正式矩阵及二十二轮默认档后，`retired-windows.json` 确认预览父窗口和视频子窗口均销毁，包括隐藏窗口；`retirement-checks.json` 实际读取线程描述，确认预览、导出、loopback、microphone 工作线程及所属临时录像文件退役。Port 的唯一编码调度服务线程仍按运行时生命周期保留。默认档总句柄 929 在两分钟空闲后为 826，文件 60→53、线程句柄 35→25、ALPC 103→54；与初次窗口／媒体初始化缓存、系统延迟释放分开报告，未将工作集修剪当作所有权释放证明。完整逐轮类型及 PrivateBytes／工作集记录保留在两个 `handles.json`。
